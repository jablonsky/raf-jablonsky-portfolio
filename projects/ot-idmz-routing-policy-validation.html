Validating OT-to-IDMZ Routing and Firewall Policy

A controlled positive-and-negative test showing that one authorised OT source can reach the industrial DMZ while reverse initiation and an unauthorised OT source remain blocked.

Validation question Architecture PAN-OS 11 transition Expected behaviour Policy under test Positive test Negative tests Results Conclusion Next validation

The problem

Can one required OT-to-IDMZ path work without creating broad access?

A diagram and a set of firewall zones do not prove segmentation. The lab needed observed evidence that a deliberately authorised flow would succeed and that closely related but unauthorised flows would fail.

The test focused on ICMP because it provides a simple, repeatable way to validate addressing, routing, stateful return traffic, and security-policy selection. It is a connectivity checkpoint rather than a claim that the production-style application design is complete.

Original PAN-OS 10 validation: Pass

The selected OT Core address reached the selected IDMZ address. An IDMZ-initiated test and a test from an unauthorised OT endpoint were blocked as expected. These results remain the historical baseline and will be repeated on the replacement PAN-OS 11 firewall.

Lab architecture involved

Three zones, one firewall control point

The PNETLab topology connects the IT, industrial DMZ, and OT networks to separate Layer 3 interfaces on a Palo Alto VM-Series firewall. The OT Core reaches the firewall over the 10.20.10.0/30 transit, while the IDMZ switch uses the 10.30.10.0/24 segment.

Controlled platform change · October 2026

The lab firewall moved from PAN-OS 10 to PAN-OS 11

The original routing and policy evidence in this article was captured on the PAN-OS 10 firewall. A problem with that virtual appliance image made it unsuitable as the continuing lab baseline, so the firewall was replaced with a new PAN-OS 11 PA-VM running as Proxmox VM 102.

This was a platform replacement rather than a topology redesign. The replacement firewall keeps the established bridge mapping, Layer 3 addresses, Zone-IT, Zone-OT, Zone-IDMZ, VR-LAB, static routes, and narrowly scoped security-policy design. The old firewall remains powered off to prevent duplicate addressing.

Evidence boundary

The screenshots and positive/negative policy results below remain valid evidence of the original PAN-OS 10 test. Successful interface tests on PAN-OS 11 prove that the replacement is connected, but the complete OT-to-IDMZ test set must be rerun before the migration itself is classified as fully validated.

A more explicit Interface Management Profile

The PAN-OS 11 baseline also tightens control-plane testing. The earlier broad permitted networks are replaced with explicit /32 source addresses for the adjacent infrastructure devices. This is an Interface Management Profile applied to data-plane interfaces; it is not the dedicated management interface.

Permitted sourcePurpose
10.10.10.1/32IT router testing the IT-facing PA interface
10.20.10.2/32OT core testing the OT-facing PA interface
10.30.10.2/32IDMZ switch when ping testing of the IDMZ-facing PA interface is required

A ping addressed to a firewall interface is controlled by this profile. A ping passing through the firewall is controlled by Security Policy. Tightening the management profile therefore does not replace or broaden the inter-zone rule being validated.

See the complete replacement and data-plane procedure in Configuring Palo Alto VM-Series for a Three-Zone OT Lab.

Acceptance criteria

Define the expected result before testing

  • Authorised flow: OT Core 10.20.10.2 can ping IDMZ destination 10.30.10.2.
  • Stateful return traffic: replies associated with the authorised session can return to the source.
  • Reverse initiation: the IDMZ cannot initiate a new ICMP session towards the OT network.
  • Source restriction: another OT endpoint, 10.110.10.100, cannot use the OT Core's specific allow rule.

This combination matters because a successful ping alone could be produced by an overly broad rule. The negative tests provide evidence that the source and direction restrictions are meaningful.

Configuration being validated

A narrowly scoped OT-to-IDMZ test rule

The policy table contains an explicit rule named test-OT-to-IDMZ-ping. It permits the ping application from the OT zone using source 10.20.10.2/32 to the IDMZ zone using destination 10.30.10.2/32. A following OT-to-IDMZ deny rule and the default inter-zone deny behaviour prevent broader communication.

Positive test

The authorised OT Core flow succeeds

The OT Core initiated five ICMP echo requests to the IDMZ switch address. All five replies returned, producing a 100% success result with a reported round-trip time of 1 ms in the virtual lab.

This result proves that the selected forward path, security rule, and stateful return path work for the tested ICMP session. It does not mean every OT source or application has access to the IDMZ.

Negative tests

Closely related but unauthorised traffic remains blocked

Two negative tests were used to challenge the rule boundaries. First, the IDMZ switch attempted to initiate traffic towards the OT transit address. Second, an OT management endpoint with address 10.110.10.100 attempted to reach the same IDMZ destination.

The gateway response in the second test is important: it separates local OT connectivity from the blocked inter-zone flow. The endpoint is operational, but it does not match the specific source permitted by the firewall rule.

Engineering conclusion

Segmentation is demonstrated through behaviour, not labels

The collected evidence shows that the firewall is enforcing the intended source and direction restrictions for this test. The permitted OT Core session crosses the security boundary successfully, while reverse initiation and a different OT source are denied.

The result is deliberately narrow. It validates ICMP behaviour for the documented addresses; it does not yet prove application-layer controls, all routing-table entries, every possible OT/IDMZ path, or production performance. Those limits are part of the conclusion rather than hidden behind a successful test.

What the evidence proves

A specific OT source and IDMZ destination communicated using the explicitly authorised test application on the PAN-OS 10 baseline, while selected unauthorised variations were blocked. The PAN-OS 11 configuration preserves that intent but requires a fresh evidence run.

Next validation step

Revalidate PAN-OS 11, then move to a realistic IDMZ service

The immediate next step is to repeat the existing positive and negative ICMP matrix on PAN-OS 11. Once equivalence is demonstrated, the following test will replace ICMP with a defined application flow, such as HTTPS, syslog, or a controlled update service.

  1. Repeat OT Core → IDMZ and confirm the explicit permit.
  2. Repeat IDMZ → OT and the unauthorised OT-source test.
  3. Correlate all three results with PAN-OS 11 traffic logs and rule hit counts.
  4. Deploy or identify the IDMZ service endpoint.
  5. Record the required source, destination, application, and port.
  6. Test the authorised connection.
  7. Repeat from an unauthorised source.
  8. Attempt an unauthorised service from the approved source.
  9. Correlate endpoint output with firewall logs, rule hit counts, and a packet capture.

This sequence keeps the image migration and the later application-policy experiment as two separate engineering claims, each supported by its own evidence.
