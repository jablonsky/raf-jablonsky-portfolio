ICMP Troubleshooting: A Systematic Approach to Network Fault Isolation

When a host cannot reach another device, ICMP can help narrow the search—but only when tests are sequenced and the source address is understood. This updated reference follows the author's original two-router troubleshooting example, retaining its addresses and historical observations.

Source: 7-page DOCS Hub – ICMP Protocol PDF supplied by the author, 25 October 2026. The original historical observations are distinguished from newly suggested verification; no fresh lab test is claimed.

1. What ICMP actually tells us

Internet Control Message Protocol (ICMP) carries network-layer control and diagnostic messages directly within IP—not over TCP or UDP. ping is a tool that typically uses ICMP Echo Request and Echo Reply, but ICMP is more than just ping.

Diagnostic / informational messages

Echo Request (type 8) and Echo Reply (type 0) support ping. ICMP also historically defined timestamp messages, but they are rarely central to modern troubleshooting.

Error and control reporting

Destination Unreachable (type 3), Time Exceeded (type 11), and Parameter Problem (type 12) help report network-layer conditions. Source Quench is deprecated and must not be relied on.

A successful Echo Reply shows that the selected source and destination can exchange the relevant ICMP messages at that moment. It does not prove that application ports, DNS, every ACL, or every network path is functioning correctly. Lack of a reply may mean loss, filtering, an unreachable destination, a return-path problem or rate limiting.

2. Original engineering scenario: isolate the fault

The source article describes a host, PC1 at 192.168.1.11, unable to reach PC2 at 172.16.1.11. The network includes two switches, two routers, a WAN transit and separate LAN subnets. The engineer has remote access to the infrastructure, but not to PC1 itself—making source selection on a router especially useful.

3. Start with interface and Layer 2 conditions

The original article begins with interface inspection rather than immediately blaming routing. The correct Cisco command is show ip interface brief (the original prose reversed the word order). The historical R1 output showed FastEthernet1/0 and Serial2/0 as up/up.

R-1# show ip interface brief
Interface          IP-Address       OK? Method Status                Protocol
FastEthernet0/0    unassigned       YES unset  administratively down down
FastEthernet1/0    192.168.1.100    YES manual up                    up
Serial2/0          10.1.1.1         YES manual up                    up
Serial3/0          unassigned       YES unset  administratively down down

Reconstructed extract based on Figure 3 of the historical PDF, not a new router capture. An up/up interface is necessary but not sufficient for complete connectivity. Review switch ports, VLAN membership, port security, line errors and ARP/MAC learning separately when indicated.

R-1# show ip route
R-1# show ip arp
SW-1# show interfaces status
SW-1# show vlan brief
SW-1# show mac address-table dynamic

Important distinction: a successful ping is not direct proof that every switch MAC table and every endpoint ARP entry is correct. Check relevant records directly; also note that the first ping may be delayed or lost while address resolution occurs.

4. Local ICMP test: R1 to PC1

First try the host's local address from R1's LAN-side interface. That checks a short, directly connected portion of the path, without depending on a remote default route.

R-1# ping 192.168.1.11
R-1# show ip arp 192.168.1.11

If the local test fails, the next investigation should focus on interface state, VLAN assignment, host addressing, host firewall, ARP and physical connectivity. The PDF describes local reachability in its original sequence, but does not provide a full independent set of switch and endpoint tables.

5. Extended ping: change the source, change the test

The original article's strongest diagnostic step is choosing R1's WAN address 10.1.1.1 as the source while pinging PC1 192.168.1.11. PC1 can reply to a local-subnet source without using its default gateway, but replying to 10.1.1.1 normally requires a correct route off the local subnet (typically via its default gateway). This makes source-specific ping a useful return-path diagnostic.

The historical Figure 5 documents 20 probes, 120-byte payload and a 3-second timeout, all unsuccessful:

R-1# ping
Protocol [ip]:
Target IP address: 192.168.1.11
Repeat count [5]: 20
Datagram size [100]: 120
Timeout in seconds [2]: 3
Extended commands [n]: y
Source address or interface: 10.1.1.1
...
Success rate is 0 percent (0/20)

Author's original diagnosis: PC1 had no default gateway configured. Technical qualification: the failed test is consistent with a missing gateway, but cannot alone uniquely prove it; filtering and host routing or return-path conditions could produce similar symptoms. Verify the PC1 IP configuration or routing information once access is restored.

6. Extend isolation toward PC2

After proving the local segment, test R1-to-R2 and then R1-to-PC2 progressively, checking both forward and return routes. The original paper reports a successful 50-probe test to PC2, using 250-byte payloads and a 4-second timeout.

R-1# ping 10.1.1.2
R-1# ping 172.16.1.2
R-1# ping 172.16.1.11
R-1# show ip route 172.16.1.11
R-1# show ip access-lists

The historical result reproduced from Figure 6 is:

That result confirms successful ICMP responses for the particular source used in the test. It is not proof that PC1 can reach PC2: PC1 may still lack its gateway, or an ACL may treat traffic differently based on source address.

7. Test the policy and return path deliberately

Where a route appears present but a source-specific test fails, check ACL direction, matching rules, routing symmetry, NAT if relevant, and destination ICMP policy. Use extended ping with a chosen source and compare results to a normal ping; then inspect the relevant configuration rather than attributing a failure to an ACL without evidence.

R-1# ping
Protocol [ip]:
Target IP address: 172.16.1.11
Extended commands [n]: y
Source address or interface: 192.168.1.100

R-1# show running-config | section interface
R-1# show ip interface fa1/0
R-1# show ip access-lists
R-2# show ip route 192.168.1.0

These commands are a suggested verification sequence, not extracted outputs from the archived test. The original Figure 8 illustrates a source-selected probe towards PC2 but does not provide a complete policy-by-policy test matrix.

9. OT engineering application

The same disciplined process is relevant when a PLC, engineering workstation, HMI or historian cannot communicate. Avoid broad configuration changes or intrusive scans during production. Establish approved diagnostic scope and use known maintenance windows where needed. ICMP may be disabled by design on OT devices, so absence of ping responses should not be treated as evidence of equipment failure.

Where a firewall separates OT zones and conduits, compare a deliberately permitted diagnostic flow with an explicitly forbidden one. A packet capture, route lookup and firewall traffic log can provide stronger evidence than ping alone.

Engineering conclusion

The lasting lesson from the author's original troubleshooting article is to isolate failure modes step by step and use tests that distinguish between competing explanations. The question is not only did ping work? but which source, which destination, which route, and what does this result actually establish?
