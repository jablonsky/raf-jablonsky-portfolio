Standard IPv4 ACLs on Cisco Routers: From Packet Flow to Verified Policy

A standard IPv4 Access Control List (ACL) looks simple: permit or deny traffic according to the source IPv4 address. The engineering challenge is deciding where to apply it, in which direction, and in what order. This article follows a two-router Cisco lab documented in my learning notes—from verifying routing to correcting an ACL entry and interpreting match counters.

1. The engineering problem

Our lab includes end-user PCs, Router 1, Router 2 and remote servers. Initially, connectivity was established with static routes and bidirectional ICMP checks. The next objective was to permit an individual host (PC1) but block a second host (PC2) in the same source subnet, while permitting PC3 and devices from its separate source subnet.

Rather than starting with a restrictive configuration, the original experiment first confirmed that routing worked. It documented successful PC1 ↔ PC3 tests, PC1 → Server 1/Server 2, and PC2 → PC3/Server 1/Server 2 before introducing the ACL. This baseline matters: if a ping fails after the policy change, we need to distinguish a deliberate filter from a pre-existing routing or addressing fault.

For clarity, examples below use the actual ACL source prefixes recorded in the notes, without assigning speculative endpoint IPs to the figure.

2. What does a standard IPv4 ACL inspect?

For normal routed IPv4 traffic, a standard ACL makes an allow/deny decision using the source IPv4 address only. It does not match destination address, TCP/UDP port, or application. Those finer controls belong to the separate extended-ACL discussion.

ACL familyTraditional numbered rangesPrimary role
Standard IPv4 ACL1–99 and 1300–1999Match IPv4 source addresses
Extended IPv4 ACL (next article)100–199 and 2000–2699Can include destination, protocol and port criteria

A standard ACL is not itself a QoS scheduler. ACLs may be referenced by other features for classification, but using permit in an interface ACL does not assign priority to voice, video, or industrial control packets. That distinction is important because the original notes explore OT packet prioritisation as a related question.

3. Which router interface—and which direction?

The notes use packet flow from PCs on the left, through R1 and R2, towards servers on the right. On R1 that direction corresponds to inbound Gi0/1 and outbound Gi0/0; on R2 it corresponds to inbound Gi0/0 and outbound Gi0/1. For a return packet, the direction relative to each interface is reversed.

For a basic standard ACL, the usual teaching rule is to place it near the destination. The reason is not that this reduces total network traffic—an unwanted flow can already have traversed much of the network—but that a source-only rule applied too early could unintentionally block that source's access to other destinations.

This distinction has a direct implication for the original scenario. If Server 1 and Server 2 are reached via the same R2 egress interface, applying standard ACL 1 outbound on that interface applies its source filtering to traffic for both servers. It cannot say “PC2 may access Server 2 but not Server 1” solely by checking the packet's source. Use separate interfaces/VLANs for suitable placement, or a destination-aware policy (the future extended ACL / firewall article).

4. The first-match rule: order is everything

Each packet is compared against ACL entries (ACEs) from top to bottom, in sequence-number order. At the first match, the corresponding permit or deny action is applied and the search stops. If nothing matches, the implicit final deny any rejects that traffic.

R-2(config)# ip access-list standard 1
R-2(config-std-nacl)# 10 permit host 10.10.10.10
R-2(config-std-nacl)# 20 deny 10.10.10.0 0.0.0.255
R-2(config-std-nacl)# 30 permit 10.0.0.0 0.255.255.255
R-2(config-std-nacl)# 40 deny any
R-2(config-std-nacl)# end

These are the exact logical source rules recorded in the notes, expressed with sequence numbers. Line 10 makes a single-host exception. Line 20 denies other sources from 10.10.10.0/24. Line 30 permits sources in 10.0.0.0/8 that have not already matched an earlier line. Line 40 makes the last deny visible. Do not swap lines 20 and 30: the larger permit range would then match the denied /24 before the router reached the deny.

5. Wildcard masks: why the numbers look backwards

Where a subnet mask marks network bits with ones, an ACL wildcard mask works as an inverse comparison mask: zero bits must match the configured source, and one bits are ignored. For ordinary contiguous network masks, the wildcard is the bitwise complement of the mask.

MatchCisco standard ACL source syntaxMeaning
One IPv4 hosthost 10.10.10.10Equivalent to address with wildcard 0.0.0.0
Subnet /2410.10.10.0 0.0.0.255Last eight address bits ignored
Network /810.0.0.0 0.255.255.255Last 24 address bits ignored
Any IPv4 sourceanyEquivalent to 0.0.0.0 255.255.255.255

A small correction to the original notes: the wildcard value 255, not 225, ignores an entire octet. More precisely, wildcard masks are evaluated bit by bit—an octet need not be only 0 or 255.

6. Configure the ACL and attach it to R2

Defining the list is only half the work. To filter routed traffic, the ACL must be associated with the appropriate interface and direction. The documented lab applies the policy on R2, closer to the target network. The following command is an illustrative IOS-style configuration using the egress interface from the notes; confirm the real routing and server topology before deploying it.

R-2# configure terminal
R-2(config)# ip access-list standard 1
R-2(config-std-nacl)# 10 permit host 10.10.10.10
R-2(config-std-nacl)# 20 deny 10.10.10.0 0.0.0.255
R-2(config-std-nacl)# 30 permit 10.0.0.0 0.255.255.255
R-2(config-std-nacl)# 40 deny any
R-2(config-std-nacl)# exit
R-2(config)# interface gigabitEthernet0/1
R-2(config-if)# ip access-group 1 out
R-2(config-if)# end

R-2# show access-lists 1
R-2# show ip interface gigabitEthernet0/1

Applying the filter outbound here evaluates routed IPv4 packets leaving R2's Gi0/1. Some device-local traffic, hardware-forwarded traffic and platform-specific control traffic can behave differently; always check the actual platform's documentation. Inbound ACL placement would examine arrival traffic on the chosen interface instead.

7. Fixing a mistake without rebuilding the whole ACL

In the original lab, sequence 30 was initially entered incorrectly. The author corrected the entry from within named-style standard ACL configuration mode:

R-2# configure terminal
R-2(config)# ip access-list standard 1
R-2(config-std-nacl)# no 30
R-2(config-std-nacl)# 30 permit 10.0.0.0 0.255.255.255
R-2(config-std-nacl)# end
R-2# show access-lists 1
R-2# copy running-config startup-config

This is a valuable real-world lesson. IOS displays ACEs by their sequence numbers (10, 20, 30…) to enable ordered modification. The numbering is an editable position marker, not an automatic indication of how packets are classified.

Operational caution: removing entry 30 from an ACL already applied to an interface changes policy immediately. Between deleting and restoring the rule, affected traffic may be denied by a later rule or implicit deny. In production OT networks, use change control, a verified rollback plan and an approved maintenance window where appropriate.

8. Explicit deny versus implicit deny—and counters

Every non-matching packet reaches the implicit deny at the end of an ACL. Adding an explicit final deny any normally preserves this result while giving the administrator a visible ACE that can have a match counter. This supports diagnostics, although counters are platform- and forwarding-path-dependent.

R-2# show access-lists 1

Standard IP access list 1
    10 permit host 10.10.10.10 (5 matches)
    20 deny 10.10.10.0, wildcard bits 0.0.0.255 (12 matches)
    30 permit 10.0.0.0, wildcard bits 0.255.255.255 (30 matches)
    40 deny any (8 matches)

Illustrative output based on the example in the linked “Explicitly deny” note, not live counters from a verified new lab run.

The 12 matches at line 20 mean those packets matched the subnet deny; the 8 at line 40 reached the final rule. But counters need careful interpretation: hardware acceleration, device model, logging and reset behaviour influence visibility. Do not use an ACL counter as a universal packet-accounting source.

The rule permit any is not a replacement for a final deny: it explicitly permits all remaining sources and makes any later deny any unreachable. Conversely, deny any as the sole ACL entry blocks every matching routed packet in that interface direction.

9. Verify the intended behaviour

The notes include a useful before/after story: connectivity was verified before deploying access controls, and PC3 later regained access to Server 1 after correcting the rule. We can turn that into a repeatable verification plan:

Send pings from both directions where permitted and helpful, but remember a standard ACL is stateless: ICMP Echo Request and Echo Reply have different source addresses and may encounter different policies. A one-way failure does not uniquely prove the cause. Interpret routing, interface direction and policy together.

10. What does this teach us about OT design?

Standard ACLs are useful as simple source-address controls, but their limited granularity makes them unsuitable as the sole segmentation mechanism between important OT zones. A real design needs to consider which communication paths are authorised, the physical and logical conduits, availability consequences, diagnostic access and how traffic is logged.

Do not confuse a packet-filtering ACL with industrial traffic prioritisation. QoS can use classifiers, but the scheduling or marking behaviour comes from separate QoS features. For the next chapter, extended IPv4 ACLs will explain source plus destination address, protocol and port matching—and why that makes them more appropriate for the Server 1 versus Server 2 policy problem.

A firewall may provide more expressive controls and visibility where security zones require them, but device and architecture choice should follow a documented communication matrix and risk assessment.

Engineering takeaway

A correct ACL is not just a correct line of Cisco syntax. It is a tested policy tied to a particular traffic path: which source, which destination interface, which direction and which first matching rule? The original sequence-30 correction is a good illustration of why precise verification and controlled changes matter as much as configuration knowledge.
